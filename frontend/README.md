# Casa de Aurum — Frontend

Real, working frontend pages wired to the backend built so far (Modules 1–4:
project setup, database, auth, user management).

## Two frontend formats exist in the original design files — read this first

The uploaded design bundle contains two different sets of pages:

1. **Top-level `*.dc.html` files** (Admin Users.dc.html, Tool Dashboard.dc.html, etc.) — these use Anthropic's internal "Design Canvas" preview format (`support.js`, `<x-dc>`, `{{ }}` template bindings). They're excellent for visual design iteration but are a declarative, data-only templating layer — not a general app runtime I can safely wire to live `fetch()` calls without a way to test the result (their CDN dependencies for React/Babel aren't reachable from my sandbox, so I can't verify changes to them actually work).
2. **The `casa-de-aurum-handoff` bundle** (numbered `00`–`06`, what this folder is built from) — genuine standalone HTML/CSS/vanilla-JS. Real DOM, real `<script>` tags I fully control and can test.

I used **option 2** so every page I touched is real, tested code — not a plausible-looking mockup. Same design system (fonts, colors, components) either way.

## What's wired in this delivery

- **`dashboard.html`** (nav fixed, Module 28) — a real navigation row now links to all ten other pages in the app (Mood Board/Print Board tool, Catalog Upload, Design Rules, Reference Images, Customers, Users, API Keys, System Logs, Analytics, Settings). Previously the only outbound link was to Staff Management, even though every one of those pages links *back* to the dashboard — meaning most of the app was reachable only by typing an exact URL. `login.html` also defaulted to redirecting a freshly-authenticated user to Staff Management rather than the dashboard; fixed to default to `dashboard.html`.

- **`login.html`** (new) — real login form. Calls `POST /auth/login`, stores the session, redirects back to whatever page sent the user here.
- **`assets/api-client.js`** (new) — shared client every page includes. Handles the access token, silent refresh via the httpOnly cookie, and typed methods for every endpoint this build has: `auth.*`, `users.*`, `me.*`, `roles.*`, `dashboard.*`, `catalogExtractor.*`, `designRules.*`, `referenceImages.*`, `moodBoards.*`, `printBoards.*`, `apiKeys.*` (list/create/rotate/activate/deactivate/remove), `settings.*` (getAll/getCategory/updateCategory), and `admin.*` — grown across Modules 21-23 to cover logs/logActions/analytics, the newer `loginHistory`/`errorLogs`/`catalogLogs`/`moodBoardLogs`/`printBoardLogs` log views, and `queueStats`/`queueJobs`/`retryJob` for the background job queues.
- **`assets/notifications.js`** (new, Module 20) — shared toast notification system (`window.CasaNotify`: `.success()`, `.error()`, `.processing()` with a live update handle, `.exportReady()` with a clickable action link). Replaces all 19 `alert()` calls that had accumulated across five pages over the course of this build. Verified with real DOM tests via `jsdom`, including a test that loads each real page's actual HTML+JS and confirms the correct toast genuinely appears for real page actions — not just that the library works in isolation.
- **`03-user-staff-management.html`** — fully wired: live staff table (search, real roles, real status), Add Staff -> `POST /users`, Edit modal -> `PATCH /users/:id` (+ `PATCH /users/:id/role` if you're signed in as Owner), Remove -> `DELETE /users/:id`, Sign out -> `POST /auth/logout`. All the safety-guard errors from the backend (can't delete yourself, can't remove the last Owner, only Owners can reassign roles) surface as real error messages in the UI, not silent failures. The **Roles & Permissions matrix is now real** — each row maps to the actual permission string(s) that gate that resource in the backend, checkboxes reflect a role's genuine permissions, and clicking one calls `PATCH /roles/:id` immediately. Owner is fixed (can't be edited — its wildcard access is what makes permission checks treat it as a superuser), and API Keys / Admin Logs-Analytics-Queues show as permanently locked for Manager and Staff rather than offering checkboxes that would do nothing, since those routes are hard-coded Owner-only in the backend regardless of permission strings. Non-owners see the matrix read-only. Shared Devices remains "Preview only" — there's no device-pairing model in the schema at all.
- **`dashboard.html`** (new) — no page like this existed in the standalone bundle (the `.dc.html` set has an "Admin Dashboard" but it's the untestable Design Canvas format — see above), so I built one from scratch in the same design language. Calls `GET /dashboard/overview` on load: stat cards for catalogs/mood boards/print boards/tiles/brands/customers/users/design rules/reference images (each with a "+N this week" delta where relevant), status breakdown chips for catalogs and mood boards, a recent activity table, and a live DB-connectivity pill in the header.
- **`catalog-upload.html`** (new) — same reasoning as `dashboard.html`: the corresponding page only exists in the untestable `.dc.html` format, so this is built fresh. Brand-select + PDF file input + upload button, an upload history table with live status pills and a real progress bar driven by `currentPage`/`totalPages` while extraction runs, queue position while waiting, duplicate-skip counts once complete, and a "View Log" action showing the full per-run processing log. Retry and delete row actions. Every validation error the backend can return (oversized file, missing brand, non-PDF, duplicate file) surfaces inline.
- **`design-rules.html`** (new) — same reasoning again (the frontend README explicitly says Design Rules Setup wasn't included in the original handoff bundle). Draft rules grouped by section with add/edit/deactivate/delete, a live-updating compiled preview panel, a status banner showing whether the draft matches what's published, a Publish action, and version history with checkbox-based Compare (color-coded diff modal), Restore, and Delete per version.
- **`reference-images.html`** (new) — same reasoning. Upload form, a responsive image grid with a lightbox preview, search box, style/room filter dropdowns (populated from the categories endpoint), and per-card Replace (swap the file, keep the metadata) and Delete actions.
- **`04-api-keys-integrations.html`** (updated, Modules 21 & 25) — the Gemini and Google Drive cards show real configured/not-configured status with working "Manage" modals and live Test Connection buttons, unchanged from before. Module 21 made the **API Keys & Credentials table real, not preview** — backed by `ApiKey` (encrypted at rest, masked in every response), with working Add/Rotate/Activate/Deactivate/Delete actions that genuinely persist and, for Gemini, take effect on the very next Gemini call (the client checks for an active DB-stored key before falling back to `.env`). Also fixed the phone mockup's "no login needed" copy, which was accurate to the original design intent but not to this backend (every endpoint requires auth by design).

I changed the Add Staff form's fields from the original mockup (Full name / Phone-or-email / Role) to what the backend actually needs and stores: **Full name / Email / Temporary password / Role**. **Verified end-to-end** — not just checked for syntax errors. ## Running it

The backend needs to actually be running for any of this to work:

```bash
cd ../backend
npm install && npx prisma generate && npx prisma migrate dev
npm run prisma:seed
npm run dev          # http://localhost:5000
```

Then serve this folder as static files (any static server works — the pages use `fetch`, so `file://` won't work for CORS reasons):

```bash
cd frontend
npx serve .           # or: python3 -m http.server 8080
```

Open `login.html` and sign in with any seeded user, e.g. `owner@casadeaurum.com` / `ChangeMe123!`.

If your backend isn't on `http://localhost:5000`, set this before `api-client.js` loads on every page:
```html
<script>window.CASA_API_BASE = "https://your-api.example.com/api/v1";</script>
<script src="assets/api-client.js"></script>
```
